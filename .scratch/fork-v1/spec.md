# ChatAtlas Fork V1

Status: ready-for-agent

验收状态：用户已最终确认包含本轮补充和一致性修订的 Spec，作为 Fork V1 正式功能验收基线。

## Problem Statement

用户在与 AI 交流时，可能希望从某个历史位置探索另一条思路，也可能只是想深入了解当前方案涉及的陌生知识。直接在原 Conversation 中继续追问，会把探索内容混入原来的讨论路径；另开独立对话又需要重新解释背景。

ChatAtlas 需要让用户从明确的历史位置准备另一条对话，在保留完整背景的同时保持原对话不变，并在细粒度对话地图中区分历史 Turn、正式 Conversation 和尚未提交的分支草稿。

## Solution

用户从一个正常完成的 Turn 对应的 AI 回复结束位置执行 Fork，创建并编辑分支草稿。草稿依赖从树根到该 Turn 的完整历史，包括该 AI 回复本身；用户可以保存、恢复或取消草稿。首次提交新的 Prompt 时，才创建独立的 Forked Conversation 和首个新增 Turn，随后生成 AI 回复。

历史由共享 Turn 组成，Conversation 表示具有独立身份的一条完整有序路径。原 Conversation 不受新分支的输入、生成、停止或删除影响。同一 Project 可以容纳多棵 Turn Tree、多个 Conversation 和多个独立分支草稿。

以下内容汇总已有访谈决定、已采纳架构和本轮明确批准的提交规则，共同构成用户已最终确认的功能验收基线；来源和批准范围见 Further Notes。

## User Stories

1. 作为用户，我希望从历史 AI 回复处探索另一条思路，以便保留原来的讨论方向。
2. 作为用户，我希望从涉及陌生知识的历史回复处深入追问，以便学习细节而不打断原 Conversation。
3. 作为用户，我希望从正常完成的 AI 回复结束位置执行 Fork，以便获得明确且稳定的历史起点。
4. 作为用户，我希望在没有符合条件的 AI 回复时使用 New Chat，以便直接开始独立对话。
5. 作为用户，我希望不能从仍在生成、主动停止、失败或因输出上限截断的 AI 回复直接 Fork，以便明确区分内容固定与正常完成。
6. 作为用户，我希望新分支继承截至选中 Turn 的全部祖先历史及该回复本身，以便无需重述已有背景。
7. 作为用户，我希望新分支不继承起点之后的原对话内容，以便从所选位置探索新的方向。
8. 作为用户，我希望 Fork 后先输入新的 Prompt，以便明确决定新分支要讨论什么。
9. 作为用户，我希望点击 Fork 时只创建分支草稿，以便在尚未确定问题时不产生空白正式对话。
10. 作为用户，我希望草稿自动保存，并能在导航离开、刷新或重新启动应用后恢复，以便继续准备未提交的 Prompt。
11. 作为用户，我希望在同一 Project 中保存多个独立分支草稿，以便同时准备不同方向的问题。
12. 作为用户，我希望能在同一历史 Turn 上准备多个草稿，以便比较不同的提问思路。
13. 作为用户，我希望取消或删除草稿不会留下正式 Conversation，以便保持对话集合清晰。
14. 作为用户，我希望首次有效提交 Prompt 时建立正式 Conversation 和新增 Turn，以便即使 AI 之后失败也保留本次真实提问。
15. 作为用户，我希望不同草稿分别提交后得到独立 Conversation，以便分别继续各条探索路径。
16. 作为用户，我希望从不同 Conversation 中看到的同一个历史 Turn 执行 Fork 时继承相同历史，以便结果不受浏览入口影响。
17. 作为用户，我希望在 Forked Conversation 的后续合格 Turn 上再次 Fork，以便逐层展开探索。
18. 作为用户，我希望普通“+”继续操作在当前 Conversation 末尾新增 Turn，以便沿原路径交流而不额外建立 Conversation。
19. 作为用户，我希望 Node Card 表示一轮已提交 Prompt 及其 AI 回复记录，以便读懂地图中的交流过程。
20. 作为用户，我希望草稿编辑卡与正式 Turn 的 Node Card 有明确区别，以便知道哪些内容尚未提交。
21. 作为用户，我希望 New Chat 开启 Independent Conversation 的新历史路径，以便在同一 Project 中组织多棵对话树。
22. 作为用户，我希望 Fork 不修改原 Conversation 或已有历史内容，以便随时回到原讨论。
23. 作为用户，我希望独立删除某个 Conversation 而不连带删除其他 Conversation，以便单独管理不再需要的对话。
24. 作为用户，我希望删除 Conversation 后其他对话使用的共享历史仍可读取，以便保留完整上下文。
25. 作为用户，我希望删除 Conversation 后已有草稿仍可恢复和提交，以便未完成的准备工作不被破坏。
26. 作为用户，我希望不同 Conversation 的 AI 回复能够并行生成，以便独立推进多条讨论。
27. 作为用户，我希望停止或失败仅影响对应 Conversation 的生成任务，以便其他对话正常进行。
28. 作为用户，我希望当前 Conversation 的回复结束前暂不能提交下一轮 Prompt，以便保持轮次顺序明确。
29. 作为用户，我希望主动停止或失败后保留原 Prompt 和实际生成的内容，并可继续下一轮，以便不丢失已有交流。
30. 作为用户，我希望继承历史中的未正常完成 Turn 按实际保存内容提供给模型，并明确其结束状态，以便模型不会将部分回复当作完整回答。
31. 作为用户，我希望 AI 未输出内容时不虚构历史回复，以便上下文准确反映实际交流。
32. 作为用户，我希望草稿默认使用分叉起点 Turn 的模型，并能在提交前更换，以便控制新分支的生成选择。
33. 作为用户，我希望默认模型不可用时保留草稿，并由我选择可用模型后再提交，以便避免系统静默替换模型。
34. 作为用户，我希望完整历史加新 Prompt 超过模型上下文容量时得到明确提示并保留草稿，以便调整模型或 Prompt 后重试。
35. 作为用户，我希望系统不通过静默截断或自动摘要来规避上下文超限，以便“完整继承”具有可信含义。
36. 作为用户，我希望 V1 完整继承受支持的纯文本历史，包括已保存的中断回复内容，以便在已支持范围内可靠探索。
37. 作为用户，我希望历史包含当前无法正确继承的图片、文件或工具调用内容时，在创建草稿前得到限制说明，以便不会误以为已经保留全部背景。
38. 作为用户，我希望同一草稿重复点击提交或因网络异常重试同一次提交时只对应一个正式 Conversation，并在明确未创建对话的失败后可以重试，以便安全完成提交而不产生重复对话。

## Implementation Decisions

### 已采纳的领域架构

以下决策来自已获 Q34 批准的 ADR-0001 和 ADR-0002。

- Turn Node 与 Turn 是同一领域对象；Node Card 是 Turn 的界面呈现。一个 Turn 包含一条已提交用户 Prompt 及其对应 AI 回复记录，回复可以尚未产生、仅部分产生或正常完成。
- Turn Tree 的结构根是首个 Turn。Independent Conversation 开启初始历史路径，但 Conversation 身份不是树中的结构节点。
- Conversation 有独立身份，并表示使用共享 Turn 的完整有序历史路径。分支共享既有 Turn 的身份，不通过复制历史建立另一套过去。
- Fork 的结构来源是选中的 Turn，记录 forkFromTurnId；不记录 createdFromConversationId，不以最初生成 Turn 的 Conversation 确定其所有权。浏览入口不改变结构关系。
- 删除 Conversation 不级联删除其他 Conversation。所有仍被 Conversation 或有效分支草稿使用的 Turn 及必要祖先历史必须保留；无需保留已删除 Conversation 的身份。
- 所有已结束 Turn 的历史内容只读，包括正常完成、主动停止、生成失败和输出上限截断后的实际内容。向模型说明结束状态属于上下文构建信息，不修改原始消息。
- 分支草稿是可独立保存、恢复的准备内容，不是正式 Conversation 或 Turn。点击 Fork 创建草稿，首次有效提交 Prompt 时才创建 Forked Conversation 和首个新增 Turn，不以 AI 回复成功为成立条件。
- 取消未提交的草稿不会留下正式 Conversation。有效草稿保护其起点和必要祖先历史；草稿删除后，不再被引用的历史可进入后续清理策略。

### 功能验收规则

以下规则沿用此前访谈决定，并纳入本轮已确认的同一草稿提交语义。用户已最终确认本 Spec 作为正式功能验收基线；这与 ADR 是否 accepted 是不同的批准范围，不要求将每条功能规则另行升级为 ADR。

**起点与地图操作**

- Fork V1 面向 ChatAtlas 内的对话历史。起点是整个正常完成的 Turn 对应的 AI 回复结束位置，不是消息中的选中文本，也不是用户消息。
- “正常完成”不等于“内容不再变化”。仍在生成、主动停止、生成失败和因输出上限截断的回复都不能直接作为起点。没有符合条件的 AI 回复时使用 New Chat，无需提供首次提问前的 Fork 入口。
- 继承范围为树根至起点的完整有序历史，包含选中 Turn 的用户 Prompt 和 AI 回复，排除起点之后的其他 Turn。
- Fork 后进入草稿编辑，等待新 Prompt，不自动重新生成起点的 AI 回复。探索另一种方案和追问当前方案的知识细节使用相同流程。
- “+”在当前 Conversation 末尾继续对话，仅新增下一轮 Turn。历史位置上的另一条探索路径通过 Fork 建立。New Chat 发起 Independent Conversation，并在产生首个 Turn 后形成新树的结构根。
- 同一 Project 可拥有多棵 Turn Tree。Forked Conversation 可以继续 Fork，V1 不人为限定分叉层数。

**草稿与正式对话的生命周期**

- 草稿在地图中使用临时 Prompt 编辑卡，不作为正式 Turn Node。草稿自动保存，并提供恢复入口，支持离开页面、刷新或应用重启后恢复。
- 同一 Project 允许多个独立草稿，包括同一起点上的多个草稿。准备新草稿不要求先提交或取消其他草稿；此规则采用用户对 Q18 的最终更正。
- 每次明确执行 Fork 创建独立草稿，不自动复用已存在的分支；分别有效提交的草稿建立不同的 Conversation 身份。点击 Fork 本身不提前创建正式 Conversation。
- “首次有效提交”指通过提交前限制检查、被应用接纳并保存的新 Prompt。模型不可用或上下文超限等业务规则阻止提交时，保留草稿且不得创建正式 Conversation；AI 在正式提交后生成失败，则保留已经成立的 Conversation 和 Turn。
- 同一草稿首次成功提交后，只能创建一个正式 Conversation；草稿退出可提交状态，并关联该 Conversation。这里的成功以正式 Conversation 已创建为准，不以客户端收到成功响应或 AI 回复生成成功为准。
- 重复点击提交或因网络异常重试同一次提交，不得创建重复 Conversation。响应丢失不能被视为已经确认“未创建”；若 Conversation 已创建，重试仍对应原 Conversation。
- 如果首次提交明确失败且未创建 Conversation，允许重试。Conversation 创建成功后，即使后续 AI 生成失败，重试同一次草稿提交也不得创建新的 Conversation。
- 不同草稿仍可分别创建独立 Conversation，即使来自同一个 Turn。上述唯一性约束针对同一草稿，不合并不同草稿的提交，也不新增 AI 回复重新生成功能。
- 新分支的后续输入、生成、停止和删除不修改原 Conversation 的历史路径及内容。

**生成状态与上下文**

- 不同 Conversation 拥有独立生成任务及状态，允许并行生成；停止或失败只影响对应任务。同一 Conversation 当前回复结束前，不允许提交下一轮 Prompt。
- 主动停止、失败或截断后保存原 Prompt 以及实际已生成的 AI 内容。用户可以继续下一轮；后续正常完成的 Turn 可以成为 Fork 起点。
- 构建模型上下文时，完整使用继承路径中实际保存的文本。对历史中的非正常结束回复附加明确的结束状态说明，避免误认为完整回答；说明与原始消息内容分离。AI 未产生内容时不虚构 AI 回复。
- 默认选择分叉起点 Turn 使用的模型，允许提交前更换。如果默认模型不可用，仍可准备和保留草稿，但提交前必须由用户选择可用模型，不静默切换。
- 完整历史及新 Prompt 超过所选模型的上下文容量时，阻止提交、说明原因并保留草稿。用户可尝试改选模型或缩短新 Prompt；不得自动摘要或截断继承历史。
- 领域模型不永久限定为纯文本。V1 优先支持完整纯文本历史，包含历史中断回复的实际文本。若继承路径中存在当前不能正确支持的图片、文件或工具调用内容，明确说明并在创建草稿前阻止该 Fork，不能静默丢弃后宣称完整继承。

### 实现组织的边界

仓库目前没有业务模块、存储实现或模型服务接口，因此不存在可直接复用的实现。需要实现的职责包括地图交互、草稿保存与恢复、Conversation 与历史路径管理、上下文构建以及独立生成任务协调；这些是行为职责，不预先规定必须拆分为多少模块。

本 Spec 不选择前端框架、数据库、模型供应商、具体 API 协议或存储表结构。模型服务的并发额度和调度属于工程约束，不能改变 Conversation 独立的领域语义。

## Testing Decisions

### 已确认的测试边界

用户在 to-spec 阶段明确确认：以用户通过应用界面完成 Fork 的完整流程为一个主要测试边界。优先从这一最高层入口验证外部行为，避免为内部函数、组件和存储细节分别建立重复测试约束。

- 测试覆盖地图交互、草稿生命周期、Conversation 与历史管理、上下文构建及生成任务协调这些职责的集成行为，不要求它们采用特定模块划分。
- 模型服务使用可控替身，模拟正常完成、流式输出、主动停止、失败及输出上限截断，并记录实际收到的上下文请求。它是控制外部依赖的测试设施，不是新增一套内部领域测试入口。
- 保存、删除及恢复测试走实际持久化流程。在隔离的测试数据环境中重新打开应用或重建应用会话，验证内容确实可以恢复，不仅检查当前页面或内存状态。
- 同一草稿的提交测试覆盖快速重复点击、Conversation 已创建但成功响应丢失后重试，以及明确未创建 Conversation 的失败后重试。通过应用可读取的正式对话及其身份、草稿提交状态和关联结果验证，不仅检查提交按钮是否禁用，也不依赖数据库表结构。
- 好的测试断言用户可见结果、可恢复的真实记录以及发往模型的请求，不断言内部函数调用次数、组件树、私有字段或数据库表设计，也不依赖真实 LLM 的措辞和随机性。
- 目前仓库没有测试框架、业务实现或类似测试可供参考。本次只确定测试边界和行为场景，不虚构既有测试惯例，也不指定测试工具。

### 关键验收场景

| 场景 | 可观察的预期结果 |
| --- | --- |
| 从正常完成的历史 Turn 执行 Fork | 出现草稿编辑状态；尚无新增正式 Conversation；等待输入 Prompt。 |
| 从不合格回复发起 Fork | 仍在生成、停止、失败或输出上限截断的回复不能直接作为起点。 |
| 从中间 Turn 分叉并提交 | 模型收到按顺序排列的祖先历史、起点内容及新 Prompt；不含原路径起点后的内容；原对话保持不变。 |
| 从不同 Conversation 中共享的同一 Turn 分叉 | 两条新分支继承相同的历史前缀；分别提交后拥有不同 Conversation 身份。 |
| 同一起点反复创建并分别提交草稿 | 不复用已存在的分支；产生独立的正式对话。 |
| 同一草稿首次成功提交 | 只新增一个正式 Conversation；草稿退出可提交状态，并关联该 Conversation。 |
| 同一草稿快速重复点击提交 | 最终只创建一个正式 Conversation，后续重复提交仍对应同一 Conversation 身份。 |
| Conversation 已创建，但成功响应因网络异常丢失，随后重试同一次提交 | 恢复或读取结果后仍只存在原 Conversation；草稿关联该 Conversation，不新建重复对话。 |
| 首次提交明确失败且未创建 Conversation，随后重试 | 失败后不存在新增正式 Conversation；允许重试，重试成功后该草稿只对应一个正式 Conversation。 |
| Conversation 创建成功后 AI 生成失败，随后重试同一次草稿提交 | 保留原 Conversation 和实际 Turn 内容；重试不新建 Conversation，也不将草稿恢复为可创建另一 Conversation 的状态。 |
| 多个草稿保存后重开应用 | 各草稿内容及起点可独立恢复，继续编辑或提交互不覆盖。 |
| 取消未提交草稿 | 不遗留空白正式 Conversation，也不修改原对话。 |
| 首次有效提交后 AI 立即失败、未输出内容 | Conversation 和新增 Turn 已存在，原 Prompt 保留；不虚构 AI 内容；可继续下一轮。 |
| 删除一个 Conversation | 其他 Conversation 可继续读取、使用共享历史；有效草稿仍可恢复和提交；被删除的身份无需保留。 |
| 删除最后一个使用某些历史的草稿 | 不破坏其他对话或草稿；不要求 V1 立即物理清理已无引用的 Turn。 |
| 两个 Conversation 同时生成，其中一个停止或失败 | 另一个继续生成；各自保留真实结果；同一 Conversation 生成未结束前不能提交下一轮。 |
| 历史含中断 Turn，后续正常完成 Turn 被选为起点 | 请求包含中断 Turn 的原 Prompt 和实际 AI 文本，并单独说明结束状态；原始历史内容未被改写。 |
| 历史中 AI 从未输出内容 | 请求不包含虚构的 AI 回复，同时仍能表达该 Turn 的实际结束状态。 |
| Fork 后未手动更换模型，且起点模型可用 | 草稿默认模型与分叉起点 Turn 使用的模型一致；提交后的生成请求使用该模型，而不是当前浏览 Conversation 的其他 Turn 所用模型。 |
| 起点模型不可用或用户更换模型 | 默认仍遵循起点模型继承规则，不静默替换；草稿可保留；不可用模型阻止提交且不创建正式 Conversation；用户明确选用可用模型后按所选模型发出请求。 |
| 完整上下文超限 | 提交被阻止，原因可见且草稿保留，不创建正式 Conversation；不发出使用静默摘要或截断历史的生成请求。 |
| 草稿提交被业务规则阻止 | 对每项适用的提交前业务限制，确认没有新增正式 Conversation，草稿仍可保留并在满足条件后再次提交。 |
| 继承路径含不支持的图片、附件或工具历史 | 创建草稿前阻止 Fork 并说明原因，不静默丢弃内容。 |
| 使用“+”、Fork 和 New Chat | 分别体现原 Conversation 新增 Turn、草稿首次提交后建立分支 Conversation、独立对话开启新历史路径的差别。 |
| 从新分支的合格 Turn 再次 Fork | 继续沿该 Turn 的实际祖先路径继承，不因分支层数或浏览入口改变语义。 |

## Out of Scope

- 从用户消息、AI 回复中的选中文本或未正常完成的 AI 回复直接 Fork，以及首次提问前的 Fork 入口。
- 对同一 Prompt 重新生成回复、编辑替换已经结束的历史 Turn、分支合并或改写已有历史。
- 图片、附件、工具调用结果的完整继承机制；V1 对不能正确支持的历史明确限制，而不是把纯文本固化为永久领域约束。
- 为超限历史自动生成摘要、自动裁剪历史、默认模型不可用时静默更换模型。
- 在同一 Conversation 中当前生成未结束时提交下一轮 Prompt。
- 在核心领域模型中记录来源 Conversation、Turn 创建者归属，或为此建立操作来源日志。
- 无引用历史的具体垃圾回收算法、执行时机和物理删除机制；保留仍被引用的历史属于本 Spec 范围。
- 与 Fork 流程无关的完整 Project 管理、地图美化、独立对话管理产品扩展，以及导入其他平台对话的机制。
- 在本次 to-spec 执行中创建 Tickets、编写业务代码或测试代码、选择技术栈、执行 Git 提交或部署。
